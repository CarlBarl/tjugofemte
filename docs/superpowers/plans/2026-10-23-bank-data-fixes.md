# Bank data fixes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Card purchases are stored under the merchant's name, Enable Banking errors are understood, and stale categories on Carl's phone repair themselves on the next fetch.

**Architecture:** Three small fixes in the existing layers. `EnableBankingKit` decodes the counterparty from `remittance_information` when the other party has no name, and decodes the real error body (numeric `code`, reason in `error`, earliest allowed date in `detail.date_from`). `LocalStore` replaces the rows the user has not touched inside each fetched window, so stale text and categories cannot survive and nothing depends on dedup keys staying stable when the text changes. `AppModel.refresh()` does one full-window fetch after the upgrade so every stored row in the bank's window is re-decoded and re-categorized.

**Tech Stack:** Swift 6.2 packages, Swift Testing, GRDB 7, SwiftUI app generated by XcodeGen.

**Spec:** `docs/superpowers/specs/2026-10-23-goal-wizard-design.md`, section "Probe results". Measured facts behind this plan: memory note `reference_enable_banking_roslagens_data`.

## Global Constraints

- Branch `fix/bank-data` from `main` (f944462), its own PR, before the goal-wizard plan.
- No new network hosts; `./scripts/check-allowlist.sh` must pass.
- Rows the user categorized by hand (`category_locked = 1`) are never changed.
- Package tests: `cd Packages/<name> && swift test`; all three packages green at the end (83 tests before this plan).
- Commit messages end with the attribution lines from the session's system reminder.

## Review Focus

1. A card purchase with empty `remittance_information` and no creditor name must not fall back to the account holder's name; it stores an empty counterparty and lands in the fallback category.
2. An error body that is not JSON, or JSON without `error`/`code`, must still surface as `ClientError.http` with the status, never crash or hang.
3. A 422 whose `detail.date_from` is not later than the requested date must not retry forever; at most one retry.
4. The full-window repair fetch must not mark the repair done when the fetch fails, so the next pull tries again.
5. Replacing a fetched window must keep every manually categorized row, and must not duplicate a booking whose dedup key changed because its text changed (the fingerprint key includes the counterparty).

- [ ] **Step 3: Decode the real shape**

`ErrorBody` has `error: String?`, `message: String?`, `code: String?` and `detail: Detail?` with `dateFrom: String?` (`date_from`). A custom `init(from:)` reads `code` as a String, or as an Int turned into a String, or nil. `send` switches on `error ?? code`; WRONG_TRANSACTIONS_PERIOD with a `detail.date_from` that parses as a civil day in Europe/Stockholm throws `.wrongPeriod(earliest:)`. `transactions` wraps its loop so one `wrongPeriod` with a later `earliest` restarts from it; a second one throws.

### Task 3: Each fetch replaces the untouched rows in its window, and one full-window fetch repairs old rows

**Files:**
- Modify: `Packages/LocalStore/Sources/LocalStore/LocalStore.swift` (new `replaceUnlocked`, `Settings.fullFetchPending`, settings load and save)
- Modify: `Tjugofemte/Sources/Model/AppModel.swift` (`refresh()`, `describe(_:)`)
- Test: `Packages/LocalStore/Tests/LocalStoreTests/LocalStoreTests.swift`

**Interfaces:**
- Consumes: Task 1's corrected `TransactionRecord`.
- Produces: `LocalStore.replaceUnlocked(bookedOnOrAfter from: Date, with transactions: [Transaction]) throws -> Int` (in one write: deletes rows with `category_locked = 0` and `booking_date >= from`, then inserts the fetched rows ignoring key conflicts, so a locked row with the same key stays; returns how many were inserted). `Settings.fullFetchPending: Bool`, stored under key `full_fetch_pending`, true when the key is absent (so every existing install does one full-window fetch). The goal-wizard plan sets it again when the user raises retention.

    _ = try store.insertNew([tx("old", day(2026, 7, 22), -30, "BEFORE WINDOW", "transfer"),
                             tx("a", day(2026, 10, 1), -245, "SPAR AURLAND", "transfer"),
